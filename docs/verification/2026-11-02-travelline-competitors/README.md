## Данные и воспроизведение

Изолированная Docker PostgreSQL-схема: `hp_tl_competitors_20261102_0a0460dd`. Нативный macOS runner сохранил **5 runs, 5 jobs, 5 attempts, 39 observations, 31 variants, 128 offers**. На сбор — **10 HTTP GET**, 9543 мс, HTTP-ошибок 0. Повтор `RunQueued` не сделал HTTP и не создал записей.

Реальные исходные `room_stays` разрешённых тарифов сопоставлены с PostgreSQL по категории/тарифу: все 128 сумм, RUB и `reported_quantity` совпали. Все 136 строк данных пяти CSV сверены с БД, включая 8 строк категорий без offers. Столбцов 35. Количества разных тарифов и вариантов не складывались.

Площади берутся из `room_types[].size` и сохраняются в observation/CSV. Неизвестная площадь остаётся пустой; конфигурационная модель не расширялась. `total_rooms=null` у всех новых категорий и отелей. Aerostar сохранён: изменено только `collection.enabled`.

Артефакты: [категории](categories.csv), [сводка readback и run IDs](readback-summary.json), [HTTP manifest](request-manifest.json), [snapshot БД до HTTP](database-before.json), пять `<property_id>.csv`. Snapshot содержит два прежних изолированных smoke и текущие 5 queued jobs до первого HTTP: первая подготовка остановилась на незаданном owner; продолжены те же jobs после исправления только временного harness. Старые схемы не менялись.

Применены штатные миграции только к новой схеме. Harness использовал `CreateRun/CreateJob → RunQueued → SaveAttempt → FinishRun → WriteRunCSV`, 2 workers, существующие TravelLine limits (2 активных / 1 старт в секунду), без hotel retries и без доставки на Яндекс Диск.
