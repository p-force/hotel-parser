## Как проверяли

До миграций в новой БД не было пользовательских таблиц. Защита соединения сначала отклонила ошибочный pooler URL без записей. После исправления пользователем на direct host штатный runner применил все пять миграций и повторно проверил их checksum/идемпотентность. Будущая схема `hotel_parser_ni_teta` не создавалась.

Для smoke получен сценарий из существующего `schedule.BuildPlans()`. Штатным `PlanRun()` опубликован отдельный fixture-run с одним выбранным job; повторный `PlanRun()` не создал дубликата. Полный `plan` на всех отелей и датах не запускался. Это проверка ограниченного сценария, а не доказательство полного регулярного сбора всей группы.

Запуск выполнен через защищённый `/api/resume` временного production deployment **без назначения production-домена**, с `MAX_JOBS=1` и test-only разрешением сбора. Далее использовались штатные `Service.Execute → RunQueued → Collect → нормализация → SaveAttempt → FinishRun → CSV → delivery ledger → YandexDiskUploader`. Других HTTP-механизмов сбора не создавали. После проверки временный deployment удалён; production-домен обслуживает вариант с `COLLECTION_ENABLED=false` и актуальным direct DSN.

Время фактического сбора: **18:38:25 МСК**; подтверждение доставки: **18:38:30 МСК**. Логический слот fixture-run — **12:00 МСК**, поэтому он же указан в имени CSV; время загрузки не подменяет слот.

Метрики одного сбора из stderr JSON в `fra1`: HTTP 1432 ms, parse 11 ms, collection 1443 ms. В PostgreSQL подтверждён один collection attempt. Запросы отдельных сетевых redirect hops отдельно не инструментировались.

## Что осталось для регулярного режима

Реальный план команды — **Hobby**, подтверждён CLI API. [Legacy Cron](https://vercel.com/docs/cron-jobs/usage-and-pricing) на Hobby ограничен одним запуском в день для каждого cron и неточным временем; новый [Schedules beta](https://vercel.com/docs/schedules/limits) допускает на Hobby минимум 15 минут и 15-минутный jitter. Ни один вариант не соответствует требованию resume каждую минуту. Более редкое расписание не установлено.

Нужны Pro с подходящим механизмом расписания либо отдельно согласованный внешний HTTP trigger, обеспечивающий нужную частоту и авторизацию. Внешнему trigger также нужен штатный доступ через Deployment Protection; отключать её не требуется. Перед включением подтвердить единственный production collector: старый `arena-hotel` и старый Neon не изменялись, старые cron не выключались.

Секреты пользователь уже настроил в Production. `CRON_SECRET` пока не задан: его нужно добавить перед использованием Cron. Полный список настроек и процедура перехода на VPS: [инструкция](../README.md). При переносе использовать обычную `dev` и существующие очередь/lease/delivery ledger, предварительно остановив Vercel trigger. Историю БД и доставленные CSV удалять не нужно.
